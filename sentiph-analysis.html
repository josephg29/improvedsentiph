01 What sentiph Is

sentiph is a local web dashboard for orchestrating multiple Claude Code agents in parallel on a live canvas. Its core thesis: terminal coding agents can be composed as interchangeable building blocks inside an orchestration layer, the same way microservices are behind an API gateway.

Live Agent Canvas

Color-coded circle nodes, d3-force physics, WebSocket-streamed state — watch agents work in real time.

PTY-Backed Terminals

Each agent is a real PTY session with scrollback, lifecycle state, transcript persistence, and hook callbacks.

Pipelines v1

Deterministic build → check → fix → done routine. Schema-validated headless workers. No LLM control flow.

Child Agents & Messaging

Spawn up to 9 child agents per parent. In-memory channel queues for short agent-to-agent coordination.

Activity View

Git commit heatmap, Claude + Codex token usage charts, recent PR summary — all from local data.

Orchestration MCP

MCP server exposes build, spawn_terminal, list_terminals, etc. so agents can orchestrate each other.

Non-Goals (v1)

  • No arbitrary DAG pipelines — v1 is linear with one conditional branch.
  • No persistent message delivery — channels are in-memory only.
  • No automatic multi-level group leaders — prompt-based only.
  • No distributed or multi-machine orchestration.
Target user: A developer who needs to delegate parallel workstreams to Claude agents and wants visibility into what each one is doing — without babysitting individual terminal tabs.

03 How It Operates

Agent Lifecycle

An agent moves through these states, driven by hook callbacks — not polling:

created → live → idle → stopped → exited

Side states: queued, blocked (waiting for permission), stale (API restart — PTY lost)

Claude's hook system (UserPromptSubmit, PreToolUse, Notification, Stop) fires callbacks to the API, which transitions state, auto-names agents from their first prompt, injects channel messages at idle, and persists transcript events.

Pipeline Execution

The conductor asks a pure deterministic router (packages/core/application/pipelineRouting.ts) for the next action, then acts on it. All branching logic is isolated in the pure layer.

build → check ×N → [approval?] → fix ×M → check ×N → done

standard 2 max 1 No Default for most tasks
quick 1 0 No Trivial changes (typos, docs, renames)
careful 3 max 1 Yes (human) Risky changes (auth, payments, migrations, secrets)

04 What Is (and Isn't) Implemented

Fully Implemented

  • Interactive PTY-backed agents on canvas — create, run, stop, kill, delete, rename
  • Worktree isolation — per-agent and per-pipeline-run git branches
  • Git operations — status, commit, push, sync, PR merge via gh
  • Hook-based state machine — no polling; state transitions come from Claude's hook callbacks
  • Channel messaging — in-memory queues with idle-based injection
  • Transcript persistence — JSONL per session, append-only
  • Pure deterministic pipeline router — 100% unit tested, no LLM in control flow
  • Three recipes with auto-picker — keyword-driven, deterministic recipe selection
  • Schema validation on worker output — headless workers validated before outcomes persist
  • Bounded fix loops — no infinite retries; budget-constrained
  • Human approval gate — careful recipe pauses for human sign-off
  • Child agent spawning — up to 9 per parent, links visible on canvas
  • MCP tools for orchestrators — build, spawn_terminal, list_terminals, send_prompt, get_terminal_output
  • Activity view — git summary, Claude/Codex usage heatmap
  • UI state persistence — layout, minimized terminals, widths, sidebar, sounds all round-trip through API
  • Comprehensive CLI — sentiph terminal create/list/stop/kill/prune, channel send/list, projects, init
  • Security defaults — loopback binding, Origin/Host validation, explicit remote access opt-in

Partially Implemented

  • Conversation search — domain types exist (ConversationSearchResult, searchConversations), no UI wired up
  • Conversation export — conversationExportMarkdown function exists, no API route exposed
  • Multi-level group leaders — system prompt describes group_leader: true, no dedicated tooling or UX validation
  • Agent model/effort override — terminal creation API accepts model/effort, UI always defaults to sonnet/medium

Not Implemented (Deferred by Design)

  • DAG pipelines — v1 is strictly linear with one conditional branch
  • Persistent channels — messages are in-memory only; lost on API restart
  • Auto merge on approval — approved runs are left on their branch; human merges manually
  • Custom recipe editor UI — only three hardcoded recipes, no UI to create or tune them
  • Per-agent cost budgeting — usage is captured but no spending limits or alerts
  • Historical run timeline — current runs shown, past runs in files but no timeline view
  • Agent resource limits — no memory/CPU caps per agent
  • Distributed orchestration — single machine only

Architectural Weaknesses

IssueImpactStatus
In-memory channel queues Channel messages lost on API restart — unrecoverable inter-agent coordination state. Documented / Known
No workspace lock Two API instances on the same workspace can corrupt JSONL state files. Undocumented risk
No transcript compaction JSONL files grow unbounded over time; no size-based pruning or rotation. Minor
Per-stage fanout hardcoded Checker fanout always 2×; no per-recipe tuning. Fast to add but blocked until recipe schema is extended. Low
Headless worker timeout fixed Default 60 s per worker; no per-stage override. Long build stages may timeout; fast ones burn budget. Medium
No observability No structured logging, no metrics export, no distributed trace. Debugging live issues is console-only. Medium for teams
No authentication Secure by default (loopback only), but if SENTIPH_ALLOW_REMOTE_ACCESS=1 is set, the API is fully open. Risk if remote-access enabled
No resource isolation Child agents and pipeline workers share CPU/RAM with no caps. Noisy neighbor possible under high load. Acceptable for single-user
No pipeline resume after restart In-flight runs are failed with reason api_restart on startup. No checkpoint/resume in v1. Documented / Known

UX Gaps

  • No visual "paused at approval gate" — only a status badge, no prominent UI interruption.
  • No bulk operations — delete/stop 5 stale agents requires 5 individual actions.
  • No agent restart button — must stop and recreate; any initial-prompt context is lost.
  • No terminal search/filter — filter by name or state when canvas is crowded.
  • No undo for agent deletion — immediate, no soft-delete or recycle bin.
  • No agent grouping/labeling — all agents on one flat canvas; no project folders or tags.
  • No compare/diff view — can't side-by-side two agents' outputs or file diffs.
  • One-by-one approval — no "approve all passed runs" batch action.

Testing Gaps

  • No integration tests — mock workers everywhere; no real end-to-end agent-spawn-to-result flow.
  • No UI component tests — React components have zero unit tests despite @testing-library/react being listed as a dependency.
  • No concurrent WebSocket tests — no test for multiple clients attached to the same PTY.
  • No hook race condition tests — simultaneous hook POST and TTY output not tested.
  • No scrollback overflow test — no explicit test for the 128 KiB cap boundary.

Security

  • Binds to 127.0.0.1 by default — loopback only.
  • Validates Host and Origin headers — enforces same-origin.
  • 1 MiB JSON request cap — prevents large payload abuse.
  • Requires explicit SENTIPH_ALLOW_REMOTE_ACCESS=1 to expose remotely.
  • Gap: No authentication token when remote access is enabled. Anyone on the network can control all agents.

09 Success Forecast

Overall verdict: Technically sound, product-market fit TBD

The engineering is clean, the core insight is real, and the architecture is intentionally scoped. The biggest uncertainty is not technical — it's whether the target user (a developer managing multiple parallel Claude sessions) is real enough in number to support a product, and whether the workflow friction (setup, worktrees, hook wiring) is low enough to convert curiosity to daily use.

Why It Will Succeed

Sound core architecture

Deterministic pipeline routing with bounded loops means predictable, debuggable behavior — rare in AI tooling.

Right timing

The Claude Code ecosystem is growing fast. A native orchestration layer for it fills a real gap that no existing tool addresses.

Local-first = no cloud friction

No sign-up, no data leaving the machine, no API keys for the tool itself. Zero trust barrier to try it.

Comprehensive documentation

Rare at this stage. Concepts, guides, and references are thorough — accelerates onboarding and community growth.

Composable design

The MCP server means agents can orchestrate each other. That's a genuine force multiplier as Claude's capabilities grow.

Clean test coverage of critical logic

Pipeline routing is 100% unit tested. Regressions in the most complex logic will be caught before they ship.

Why It May Struggle

Setup friction

Requires Claude CLI, a git repo, hook configuration, and understanding of worktrees. The happy path is not five minutes.

Local-only limits scale

Can't run on a server, can't share with teammates, can't survive a laptop close. All limitations for professional use.

No auth on remote access

If a user enables SENTIPH_ALLOW_REMOTE_ACCESS=1, the API is fully open. One misconfiguration = full agent control to anyone on the network.

In-memory state loss

API restart loses all channel messages and in-flight pipeline runs. Heavy users will hit this quickly.

No UI test coverage

UI regressions won't be caught by CI. Canvas bugs and terminal state edge cases require manual testing on every release.

Narrow pipeline recipes

Three hardcoded recipes cover many cases but not all. Users who need custom flows are blocked until a recipe editor ships.

Small team risk

At 0.1.0, the codebase is one developer's work. Bus factor is high. Velocity depends on the founder's bandwidth.

Dependency on Claude CLI

Anthropic changing their hook interface, session format, or CLI flags could break agent state detection without notice.

The Three Critical Unlocks

Success depends most on three decisions, none of them technical:

  1. Onboarding speed. The first 10 minutes must work end-to-end without reading docs. Right now there are too many prerequisites.
  2. Persistent channels (or an explicit alternative). Inter-agent coordination that evaporates on restart is a trust problem. Users must write findings to files — that's a friction bump every session.
  3. Remote/team access with auth. A dev tool that only runs on one machine is a productivity tool. One that runs on a server and supports teams is a platform. The architecture supports it — the security model doesn't yet.

Top 5 Highest-Leverage Improvements

  1. Add authentication to remote access mode — even a static bearer token in config. Right now enabling remote access is a security foot-gun.
  2. Add UI component tests — the canvas and terminal components are the user-facing heart of the product and have zero automated coverage.
  3. Persist channel messages to disk — even a simple JSONL file per channel would eliminate the "restart = lost coordination" problem without redesigning anything.
  4. Expose model/effort in the create-agent UI — the API already supports it; the UI just needs a dropdown. High value for power users, low implementation cost.
  5. Add a workspace lock file — prevents accidental state corruption if two API instances run against the same project directory.
Bottom line: sentiph is a well-engineered, thoughtfully scoped v1. The core insight — deterministic conductor driving non-deterministic workers — is architecturally sound and produces verifiable, auditable pipelines. The five improvements above are all low-effort, high-impact, and would meaningfully close the gap between "promising prototype" and "daily-driver tool."
