Sentiph · orchestration model

If the parent runs in ultracode, does it still use workers & pipelines?

Short answer: the Sentiph tools stay available, but ultracode actively biases the parent toward its own dynamic fan-out — and that quietly undoes the reason pipelines exist.

⚠️
It will tend to abandon the pipeline for substantive coding tasks unless you explicitly forbid it. ultracode's standing rule is "author and run a Workflow for every substantive task by default." The Sentiph prompt's rule is "code changes → build (pipeline)." Those two instructions fight, and ultracode is the louder, more recent default.

1They're two different orchestration engines

This is the crux. "Workers/pipelines" and "ultracode" are not the same machinery — they don't share a runtime.

Sentiph MCP workers & pipelines

  • Real PTY terminals spawned over the HTTP API
  • Invoked via MCP tools build / spawn_terminal
  • build = deterministic build → check → fix conductor
  • Git worktree-isolated, schema-validated
  • Shows up as nodes on the canvas

ultracode Workflow subagents

  • Ephemeral in-process agents (Agent/Workflow tools)
  • The orchestration script is written by the LLM
  • Control flow is model-decided, per task
  • No worktree, no conductor, no schema gate
  • Invisible to the Sentiph operator UI

2It contradicts the core principle

Sentiph's whole bet was "deterministic conductor, non-deterministic workers" — keep control flow out of the LLM. ultracode is the opposite bet: the LLM is the conductor and writes the fan-out on the fly.

pipeline:  code → build → check → fix → done  (routing is pure, tested)
ultracode:  code → "let me design a workflow" → N model-chosen subagents  (routing is vibes)

That second line is exactly the "agent soup slop" you built pipelines to kill. Running the parent in ultracode reintroduces it.

3You'd also lose canvas visibility

ultracode subagents live inside the parent's process. They don't create Sentiph terminals, so they never become nodes, never get a worktree, and never hit the conductor. You'd be back to a single opaque agent doing everything — the operator canvas would show one parent and nothing underneath.

4If you want both: give the Sentiph prompt hard precedence

The fix is a one-line escalation in the orchestrator system prompt so the model can't reach for in-process fan-out. Make orchestration flow only through the MCP tools:

Orchestration happens ONLY through the Sentiph MCP tools
(build, spawn_terminal). Do NOT use the Workflow or Agent
tools, and do NOT author your own multi-agent workflows —
every code change must go through `build`; every read-only
or research task through `spawn_terminal`. This holds even
in ultracode.

With that, the parent stays clean, building still runs through the worker terminal's pipeline, and the canvas stays honest — ultracode or not.

TL;DR — available, yes; default, no. Without an explicit "MCP-only" clause, ultracode wins and you lose determinism + canvas visibility. One sentence in the system prompt reconciles them.
